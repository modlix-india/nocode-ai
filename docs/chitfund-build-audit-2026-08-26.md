# Chit Fund one-shot build: audit synthesis

> **Provenance.** 2026-08-26, local env. One prompt ("Build a simple web application to manage a small Chit Fund company ...") sent to the appbuilder agent via `scripts/clone_harness.py` (session `SYSTEM_68d8a0a0`, app `chitfund`). Analysis inputs: the 160-call transcript (`ai.ai_session_history.TOOL_CALLS_JSON`), the SSE stream, mongo dumps of the built pages/theme/app/storages, decompiled event functions, and the nocode-ai / nocode-ui / nocode-saas source. Method: four independent analysis lenses (turn budget, tooling gaps, correctness, model behaviour), then adversarial verification of each proposed tooling gap against the real tool code, then synthesis. Independently re-checked by hand before publishing: `create_role` dropping `app_code` (calls 32, 33 sent it; tool only reads `app_id`); the fabricated `UIENGINE_PRIMITIVES` set (11 of 18 names absent from nocode-ui `functions/all.ts`, 17 real names missing, `FetchData` among them, and `FetchData` appears in none of the six saved functions); the prompt contradiction (context.py "DO NOT pass `app_id`" vs the `Authorities.<APPCODE>.ROLE_<Name>` page-gate rule); the unbound theme (`application.properties` has no `themes` key); kirun-py 3.4.0 installed against `>=3.5.0`; the create_app cache race (both 404'd docs present in mongo with the reported ids; `AbstractOverridableDataService.read` turns an empty `accessCheck` into NOT_FOUND). Line numbers refer to the working tree on that date. Related fixes landed the same day (not from this run): `drive_page.initial_wait_ms`, `tail_service_logs` exception context window, per-model vision gating for DeepSeek.

Run: deepseek-v4-flash-vision-exp, 1665 s, 160 tool calls (154 ok, 6 failed), 17.59M input tokens, ~110K tokens per turn against a 112K context (context_percent 100 at the done line of bpykqt5cp.output). Hard stop at MAX_AGENT_TURNS=160 (app/config.py:187) with no closing summary.

## 1. Outcome

The prompt asked for five Owner features (dashboard totals, create group + set installment, register members, auction entry with auto-calculated next-month discounted installment, add users as Collection Agents) and three Agent features (daily route list, one-tap payment recording, copyable WhatsApp receipt). What exists: app `chitfund` plus a theme document that is not bound to the app; roles Owner(293)/Agent(294) created client-scoped while every page gate and every home-page section checks the app-scoped token `Authorities.CHITFUND.ROLE_*`, so no user can ever pass any gate; zero users hold either role; four storages with sensible schemas and no data; 10 pages of which login (8 comps, handleLogin), home (19, role-gated sections), dashboard (21 comps, 0 events, three stat cards bound to `Page.*` keys nothing sets) and route (27 comps, 4 functions running on hardcoded m1/m2/m3 members and the fixed date 2025-01-15) have content, and groups, members, auction, agents, forbidden, notFound are one-Grid shells. Functional Owner features: 0 of 5. Agent features that work on real data: 0 of 3. Runtime: an authenticated user hits the permission gate and lands on the empty forbidden page (blank white screen); the login TextBoxes draw the floating label on top of the placeholder. The run stopped because 72 of 160 turns were single add_component calls, 27 were scaffolding, 30 were research or deferred-schema retries, and 7 were lost to a create_app cache-poisoning deadlock; the model never wrote a plan, never saw a screenshot, and spent its last two turns on a doc read and a screenshot (calls 158, 159) instead of a summary.

## 3. Tooling gaps, ranked by turns saved x confidence

Where the four lenses disagree on a number, the adversarial verification figure is used.

### 3.1 No bulk / tree component authoring (45-60 turns, high) - CONFIRMED

What happened: 72 add_component calls, mean input 351 chars, 12 consecutive dashboard adds with no interleaved reasoning (stream 412-445), meaning the model already held the whole subtree. Every ToolDefinition under tools/ was scanned: nothing adds N components in one save. replace_page_definition (pages.py:453-466, handler 390-450) writes a whole tree but has no parent-key resolution, skips `_validate_properties` and `wrap_props_catalog_aware` (which add_component applies at pages.py:1022, 1033, and which caught the onLabel error at call 137), is labelled DESTRUCTIVE / "use rarely" (context.py:602), is not in HOT_TOOLS (context.py:491-526), and the clone walkthrough at context.py:1111 documents a `definition=` param that does not exist. Parallel tool calls would not have substituted: same-page add_component is fetch-mutate-PUT via `_load_save` with no version check, so concurrent adds on one page would clobber.

Fix: add `add_components(page_name, components=[{parent_key, component_type, component_key?, name?, properties?, style_properties?, binding_paths?, display_order?}], app_code, message)` next to add_component (after pages.py:1129). Pre-validate and coerce every item with the same helpers before any I/O and return all item errors at once (a 20-item batch must not fail on one bad prop and still cost a turn); then one `_load_save` whose mutate loops `p_ops.add_component` (_page_ops.py:216) in list order so a parent earlier in the list resolves; on "Parent not found" say "order items parent-first". Register in TOOLS (pages.py:2143), HOT_TOOLS, `_TOOL_NAME_TO_GROUP` and the page_operations detail list (context.py:596-598). Reword pages.py:1114 to "For a fresh page or a new section use add_components (one call per page/section); add_component is for single inserts", and update the two recipes that taught the per-component pattern: create_page's description (pages.py:276-278) and the login recipe (context.py:270-278). Fix context.py:1111 to the real params (`component_definition=`, `root_component=`). Necessary but not sufficient: the four empty pages also need functions and data wiring.

### 3.2 Model emits one tool call per turn although the loop runs parallel batches (up to 20 turns, medium) - UNVERIFIED as a model fix, harness support CONFIRMED

The provider buffers multi tool_calls (llm_provider.py:1693-1710) and dispatch uses asyncio.gather (agent.py:440), but the model never used it: 10 create_page, 7 update_page, 4 create_storage each cost a full ~110K-token round trip. No prompt sentence tells it to. Fix (prompt): add to AGENT_PERSONA "When several tool calls are independent (creating N pages, N storages, patches to different pages), emit them ALL in one message; the runtime executes them in parallel and each message costs one turn. Never batch add_component calls to the SAME page; use add_components for that." Verify the DeepSeek adapter forwards multiple tool_calls per message. Medium confidence because this model ignored several existing instructions.

### 3.3 create_page lacks `permission`/`properties`; no create_pages (~15 turns, high) - CONFIRMED

create_page_tool (pages.py:288-294) exposes only name/app_code/client_code/title/message; only update_page has `permission` (pages.py:340). Calls 51-57 were pure permission-setting. Root cause is shared with the prompt: context.py:236 "set via update_page(name=..., permission=...)", the worked example at context.py:244-249, context.py:289-290, context.py:594-595, the create_page docstring (pages.py:275-287) and app_admin.py:412-414 all prescribe the two-step flow; the model's prose at stream line 265 is that recipe verbatim. Adding the param alone would very likely not have changed the run.

Fix: add `permission` (string) and `properties` (object) to create_page_tool; in `_execute_create_page` (pages.py:250-268) set them on the POST body built by `p_ops.new_page_skeleton` (_page_ops.py:157-179), merging properties so the skeleton's `properties.title` survives. Note create_page does not go through `_load_save`/mutate, so "pass through to the same mutate" does not apply. Add `create_pages(pages=[{name, title, permission, properties}])` (one POST per page inside the tool, per-page results), register in TOOLS and HOT_TOOLS. Rewrite every prompt site listed above to show permission passed at creation.

### 3.4 Deferred-schema gate bounces valid calls and accepts unknown params (9-11 turns, high) - CONFIRMED by code cites in three lenses and the create_role verifier

`_maybe_inject_schema` / `_gate_deferred_dispatch` (agent.py:1064-1109, 1085-1120) rejects the first call of a non-hot tool unconditionally. Calls 7->8 and 66->67 were re-sent with identical args; 25, 27, 35 with args that were already valid; 0 and 1 were abandoned. agent.py:1049-1050 passes `tool_input` straight to `tool.execute` with no key check and base.py:302-306 emits no `additionalProperties: false`, which is how create_role swallowed `app_code` (3.9). The prompt's "Prefer the explicit get_tool_schema call" (context.py:44) produced 0 get_tool_schema calls.

Fix: (1) validate supplied args against the schema; if required keys are present and all keys known, dispatch immediately and append "(schema now cached)" plus the schema to the result. (2) If unknown keys are present, return `Unknown parameter(s) [...] for <tool>. Valid: [...]` with a nearest-name hint; emit `additionalProperties: False` in to_anthropic_tool. (3) Add to HOT_TOOLS: platform_doc_list, platform_doc_read, pattern_search, pattern_read, kb_app_list_sections, which_environment, create_role, assign_role, build_authority, list_users, remove_component_styles; delete lookup_api from the surface or hot it (it is `_INTENTIONALLY_HIDDEN` at context.py:538 yet reachable). (4) Do not count a synthetic bounce against max_turns. (5) Drop the get_tool_schema sentence.

### 3.5 Turn budget misstated and never surfaced per turn (~10 turns plus the lost summary, high) - CONFIRMED by code cites

context.py:104 says "The hard turn limit is 100 calls"; config.py:187 says 160. `build_turn_reminder` (agent.py:1184-1199) returns '' and appbuilder/agent.py does not override it. The model's only budget remark is at call 158 (stream 604 "Given I'm near the build budget"). context.py:101 "Aim for <=15 tool calls per user message ... past 20 STOP and ask" is incoherent for a one-shot app build and was ignored.

Fix: template the number from settings.MAX_AGENT_TURNS; override `build_turn_reminder` in AppBuilderAgent to inject `Turn {n}/{max}, {remaining} left. Pages still shells: <list from session page summaries>.` every turn, and at `remaining <= 6`: `BUDGET: stop building. Screenshot the most important page, then write the closing summary (BUILT / STUBBED / SHELL per page).` Never allow a screenshot as the final turn. Replace the <=15 rule with "For a single-message full-app build the budget is the whole turn limit; allocate it in your PLAN."

Return user id, exact authorities granted (`_conventions.make_role_authority`), and a UIEngine.Login hint. Extend assign_role with `role_name + app_code`. Add `assign_role_to_self(app_code, role_name)` via the whoami path (app_admin.py:619-631) so the builder can `screenshot_page(anonymous=false)` a gated page. Add to the security detail text: "After create_role, provision at least one test user per role, otherwise role-gated pages are untestable and the forbidden page is what every real user sees."

### 3.13 Page-event DSL save skips the hint engine; no hint for double-quoted-literal-first concat (1.5-2 turns, plus the hardcoding regression, high) - PARTIALLY CONFIRMED

kirun_events.py:670 returns the raw error; `_hint_for_compile_error` (kirun.py:458) is wired only into compile_kirun_text (:483) and save_function_from_text (:627). Two corrections: (a) routing 670 through the EXISTING engine alone is a regression, because rule index 1 (kirun.py:436, `(?:missing|expected|required).*?:\s*(\w+)`) matches "Expected: RIGHT_PAREN" and would emit the wrong GenerateEvent/EVENTS/closing-brace hint; the new rule must go at index 0. (b) The grammar bug is narrower than "bare a + b": in kirun_py dsl_parser.py:324-338 `_parse_argument_value`, single-quoted strings and numbers get an OPERATOR lookahead, the double-quoted branch (:335-338) returns a literal unconditionally. `Parent.b + 1`, `1 + Parent.b`, and `'Store.paidIds.' + Parent.memberId` all compile; only a value STARTING with a double-quoted string or boolean followed by an operator fails (also inside object literals). The venv has kirun-py 3.4.0 while requirements.txt pins >=3.5.0; 3.5.1 has the identical parser. Impact: 152 was unavoidable by a post-failure hint; 154 and about half of 153 were avoidable. The bigger cost is that after 152 the agent abandoned the dynamic `"Store.paidIds." + Parent.memberId` path and hardcoded m1/m2/m3 (153, 155).

Fix: kirun_events.py:670 -> `raw = f"{type(e).__name__}: {e}"; error=f"Compile error: {raw}\n\n{_hint_for_compile_error(raw)}"` (import from .kirun is circular-safe). Insert at `_COMPILE_HINT_RULES[0]`: pattern `Expected:\s*(?:RIGHT_PAREN|RIGHT_BRACE|RIGHT_BRACKET|COMMA)[\s\S]*Actual:\s*(?:OPERATOR|EQUALS|IDENTIFIER\s*\((?:and|or)\))` with hint "An argument value that STARTS with a double-quoted string, true/false, or null and then continues with an operator is read as a plain literal. Wrap the whole expression in parentheses: `path = (\"Store.x.\" + Parent.id)`, or start with a single-quoted string: `path = 'Store.x.' + Parent.id`. Fix only that expression; do not restructure the step." Upstream: add the same lookahead to the double-quoted and BOOLEAN branches in nocode-kirun/kirun-py dsl_parser.py:335-338 and `_parse_complex_value`, then bump the venv. Add one pitfalls line to the two DSL tool descriptions (the only layer that could have prevented 152 itself).

### 3.14 Storage rows have no seed path; prompt has no FetchData guidance (2 turns, high on the gap, low on causality) - PARTIALLY CONFIRMED

The causal claim is weak: the agent never looked for a seed path, knew FetchData (stream 139, 158), and chose literal data for demo effect (stream 550); the real defect is the missing FetchData read, not the missing seed. context.py has NO FetchData/SendData mention and no prohibition on literal rows; the "READ-ONLY rows" line at context.py:895 is inside a keyword-gated group. Never SetStore a literal array of rows as demo data; an empty storage rendering an empty list is correct." Reconcile context.py:863 with internal_api_calls.md. create_storage result (schemas.py:599): "Created storage 'member'. It has 0 rows. Read: UIEngine.FetchData(url='/api/core/data/member'); write: UIEngine.SendData. Do not hardcode rows in SetStore; to seed, author a server-side Kirun function and run it with execute_function." Secondary, only if the design rule is revised: `insert_storage_rows(storage_name, rows[], app_code?, client_code?)` via gateway POST with overridden headers, cap 50, surface onlyThruKIRun/createAuth rejections. Drop `seed_storage_sample`.

### 4.1 create_app read-back race caches a negative access answer (confirmed, needed an operator)

Reproduction: call 5 create_app: security app chitfund (id=789) created, UI override write failed "HTTP 404: Application with id 6a8e94b66259c65e1b96aa0c not found ... retry the UI write via update_app". Call 6 get_app lists the doc with that same id. Call 11 create_theme -> 404 "Theme with id ... not found" although the theme doc exists in the dump. Agent prose: "my earlier id is wrong" (stream 99), "the first 404 was transient" (114). Recovery only after an external cache eviction; the agent never called clear_cache or list_caches (infra tools appear in the prompt only as a group label, context.py:463; clear_cache's description mentions only "after a raw mongo write"; context.py has no mention of stale-after-create).

Fix locations: (platform) security app registration should publish eviction of the app-access caches, or the UI service should not cache a negative app-access answer within N seconds of app creation. (tool) `_upsert_ui_app` (app_admin.py:264-290) special-cases only 409; on "404 <Entity> with id X not found" where X came from a POST in this call, call DELETE /api/ui/internal/cache (targeted) and retry the read once, reporting "healed stale negative cache after create"; same in `_execute_create_theme` and `_execute_update_app`. (executor) if a 404-by-id arrives within 120 s of a successful create of the same entity, append "This looks like a stale negative-cache entry right after create. Call clear_cache() then retry the SAME call; do not re-create." (prompt) "If a write returns 404/403 for an id you were given by a successful create in the last few calls, call list_caches then clear_cache, retry once, then tail_service_logs; do not compare against other apps."

## 6. Model behaviour verdict: deepseek-v4-flash-vision-exp on autonomous builds

Versus the MiniMax M3 failure modes, this model was a clean executor: valid JSON args every call, no hallucinated tool names, exact-duplicate inputs only on schema bounces and the theme retry, longest same-tool failure streak 2 (152/154 differ, so the STUCK_N=4 quarantine at agent.py:292 never fired), 0 verify re-reads after writes, 67 of 72 add_component calls carried inline styles, the login recipe was followed (no Navigate on success, updateStoreImmediately set), and the ToggleButton `onLabel` error (137) was fixed from the valid-list on the first retry. Those M3 modes were absent.

What it did instead was strategic: no plan; 37 calls of bootstrap and research before the first content write (first add_component at 60); a 14-call read streak (17-30) against a 3-read cap; ten empty shells then depth-first polishing of login/home/dashboard (56 calls, 2 event functions, 0 data) before the route page (43 calls) and never any Owner workflow; it ignored build_authority (0 calls, context.py:242), get_tool_schema (0), the screenshot cadence (context.py:67; one screenshot at call 159 never viewed), and the theme binding order; during the cache incident it burned 12 calls including a 284KB read of an unrelated app without once considering clear_cache. Its recovery from the DSL error was fast but wrong in kind: it hardcoded m1/m2/m3 into business logic rather than fixing syntax, then wrote "The route page is fully wired" (stream 596). It over-claimed three times ("fully functional" at 290 with no page content, "UI is complete" at 463 with unset bindings, "fully wired" at 596) and disclosed mock data once, never as a TODO. It followed two contradictory prompt rules (context.py:1032 vs :239) faithfully into an app nobody can enter, and it re-sent `app_code` to create_role after the injected schema showed `app_id`.

Verdict: adequate for bounded edits, one page or one function per message, with a human reading each message. Not adequate for autonomous multi-page builds until the harness supplies the strategy layer it lacks. Re-run the same brief after the changes below before judging the model further; most of the damage traces to tools and prompt text, not to the model choosing to cut corners.

Prompt changes to make (quoted):

1. Plan gate, after the "Build methodically" list (context.py:36): "Before the first write on a multi-feature build, emit a numbered PLAN listing every user-facing workflow from the brief, ordered by user value (data-writing workflows first, launcher/dashboard/decorative pages last), with an estimated call count per item summing to under 70% of the turn budget. Build strictly in that order. A page that only navigates, or displays numbers nothing computes, is not a feature; spend at most 8 calls on it until every data-writing workflow exists."
2. Research scope (research cap block, context.py:110): "code_grep/code_read are for verifying a REST payload shape after a write has failed. Never open nocode-ui or nocode-saas source to learn how expressions, authorities, or bindings work; that is covered by this prompt and platform_doc_read. Never get_app a different app to compare structure." Enforce mechanically: after 4 consecutive read-only calls the turn reminder says "Your next call MUST be a write tool."
3. Roles (replace context.py:1029-1036): "Roles that back an app-prefixed page or storage gate (Authorities.<APPCODE>.ROLE_<Name>) MUST be created with app_code=<appcode> (defaults to the session app). 7. Stale cache (AGENT_PERSONA): the 4.1 text.
